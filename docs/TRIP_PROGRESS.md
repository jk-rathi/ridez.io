# Trip progress and Google navigation

Once a ride is IN_PROGRESS, the rider overview shows a prominent progress card above the other ride details. Google trips use the same authenticated, polled route response as the embedded map: estimated time remaining, expected arrival in the device timezone, remaining road distance, destination, and confirmed fare. The card and map share one request every 15 seconds; the existing server route cache can reuse a route for up to 60 seconds. These are estimates, not guaranteed arrival times. A missing/stale driver location or failed route request hides live estimates. Simulated trips explicitly show that live estimates are unavailable.

On the driver's Start trip button, the app first verifies the rider OTP through the existing backend action. Only a successful IN_PROGRESS response navigates the same browser tab to a Google Maps driving-directions URL with `dir_action=navigate`. Using the same tab avoids popup blocking after the network request. The destination uses the booked coordinates; Google uses the device's current location as the origin. Invalid OTP or request failure leaves the driver in ridez.io. Simulated rides do not open navigation.

Google Maps decides whether to open its installed app or website and whether navigation can begin immediately; some devices require tapping Start or granting location permission. There is also an Open Google Maps navigation link during an active trip, including after reloading. Return to ridez.io to complete the trip. Opening Maps can suspend browser GPS updates, so rider live estimates may become unavailable until the driver returns. Continuous background tracking across apps needs native mobile capabilities.

Validation: frontend production build; backend `tests/test_trip_map.py`; browser fixture `frontend/tests/trip-progress.browser.cjs` against Vite, covering the mobile card, stale-location fallback, shared authenticated route fetch, rejected OTP, and successful destination handoff. Browser fixtures intercept Google navigation and do not verify a physical phone's native Maps behavior.
